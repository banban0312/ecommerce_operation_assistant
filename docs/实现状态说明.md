# 实现状态说明

本文把 PRD v0.3、Spec v0.2 的设计基线与当前仓库实现对齐。开发和运维时以实际代码与根目录 [README.md](../README.md) 为准；不要把计划技术误认为已部署。

## 当前工程边界

- 当前项目按单机 Docker Compose 运行：MySQL 8.4、Redis 7.4、迁移任务、FastAPI、Celery Worker 和 Next.js Web。
- 这是本机开发/演示部署，不是公网生产部署模板。Compose 的 Web/API 端口只绑定 `127.0.0.1`；目前不包含 HTTPS 反向代理、公网访问控制、云端密钥管理或自动异地备份。
- 数据库迁移由 `api/alembic/versions/` 管理，当前迁移链截至 `0013_workspace_service_credentials.py`。容器启动前先运行 `migrate` 服务。
- 当前没有 PostgreSQL 或 LangGraph 服务。Agent 任务、步骤、审批和 JSON checkpoint 由现有 MySQL 模型保存；Spec 中 PostgreSQL checkpoint 是原阶段方案，不属于当前部署依赖。
- 角色包括管理员、运营主管和运营人员。首次管理员由 `python -m app.bootstrap` 交互创建；后续成员由管理员在成员管理页创建。系统没有默认账号或硬编码密码。

## 凭据和配置

- `scripts/init-env.ps1` 从 `.env.example` 生成被 Git 忽略的本机 `.env`，为 MySQL 和 `AUTH_SECRET_KEY` 生成随机值，不覆盖已有 `.env`。
- 管理员在系统设置页填写的工作区服务密钥会加密后存入数据库；加密密钥从 `AUTH_SECRET_KEY` 派生。`.env` 中的 Provider 密钥仍可作为未覆盖配置时的默认值。API 不向页面返回密钥明文。
- 恢复数据库备份时必须同时恢复与该数据库匹配的原 `.env`，至少保留原有数据库密码和 `AUTH_SECRET_KEY`。丢失 `AUTH_SECRET_KEY` 后，旧工作区加密密钥无法解密；新建空数据库则可重新生成 `.env` 并初始化新管理员。
- AI 内容、图片或视频任务还依赖有效的供应商密钥、模型权限和接口兼容性。容器健康不代表外部模型或媒体供应商已完成真实生成验收。

## 功能与数据

- 仓库包含商品/库存、竞品、内容版本、媒体任务、素材审核、投放审批、经营数据/复盘、CSV/XLSX 导入、系统设置、成员管理和 Agent 任务等代码。
- 运营大盘的“无线充经营演示”入口可创建带模拟标记的示例数据，便于新环境检查界面和流程；它不是生产初始化数据，也不应被解释为真实经营记录。
- M1—M12 的代码能力已经进入当前工程；GitHub Issue/Milestone 的关闭状态、真实供应商效果和需要人工操作的端到端验收记录，应分别以 GitHub 与[验收清单](validation/M9-P0验收记录.md)为准，不能仅从代码存在推断完成。
