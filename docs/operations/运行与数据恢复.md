# 运行与数据恢复

新机器从空数据库部署的完整步骤见仓库根目录 [README.md](../../README.md#新机器部署)。本文说明本机服务生命周期、持久化范围和恢复边界。

## 服务生命周期

```powershell
# 查看容器状态
docker compose ps -a

# 查看启动失败原因
docker compose logs --tail 100 mysql redis migrate api worker web

# 重启应用服务
docker compose restart api worker web

# 停止服务并保留命名数据卷
docker compose down

# 再次启动
docker compose up -d --wait --wait-timeout 180
```

`migrate` 成功运行后退出是正常的；其他服务应为 `healthy`。Docker Desktop 必须保持运行，容器才可访问。

## 哪些内容会保留

| Compose 卷 | 内容 |
| --- | --- |
| `mysql_data` | 用户、工作区、商品、库存、导入批次、内容、任务和业务记录 |
| `redis_data` | Celery 队列和结果后端数据 |
| `uploads_data` | 上传及生成的素材文件 |

`docker compose down` 只移除容器和网络，不移除这些卷。Docker Desktop 重置/卸载、手动删卷、磁盘损坏或 `docker compose down -v` 可能永久删除数据。Git 仓库不包含这些数据。

## 备份建议

当前仓库没有自动备份服务。需要保留业务数据时，定期将以下内容复制到安全的仓库外位置，并确认备份可读：

1. MySQL 业务数据库逻辑备份。
2. `uploads_data` 中的素材文件。
3. 本机 `.env`。它包含数据库凭据和 `AUTH_SECRET_KEY`，必须限制访问，不能提交 Git 或放入公开网盘。

可在 PowerShell 7.4 或更新版本中执行以下示例，生成一个本地数据库转储，并单独复制素材卷和 `.env`。目录 `backups/` 已加入 Git 忽略规则；备份仍应另存到受保护的位置。

```powershell
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$backupDir = Join-Path (Get-Location) 'backups'
New-Item -ItemType Directory -Force -Path $backupDir | Out-Null

docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysqldump --single-transaction --routines --triggers --default-character-set=utf8mb4 --user=root "$MYSQL_DATABASE"' > (Join-Path $backupDir "database-$stamp.sql")
if ($LASTEXITCODE -ne 0) { throw 'MySQL 备份失败' }

docker compose cp api:/app/uploads (Join-Path $backupDir "uploads-$stamp")
if ($LASTEXITCODE -ne 0) { throw '素材备份失败' }

Copy-Item -LiteralPath '.env' -Destination (Join-Path $backupDir ".env-$stamp")
```

备份文件可能包含用户与业务数据及高权限密钥；使用 BitLocker、受控磁盘或权限受限的备份介质保护。不要把 SQL、素材、`.env` 或真实测试报告上传到公开仓库。

## 在新机器恢复

1. 按根 README 克隆仓库。有原 `.env` 备份时，先安全恢复它（例如 `Copy-Item .\backups\.env-YYYYMMDD-HHMMSS .\.env`），再启动 MySQL；不要用新生成的 `.env` 覆盖原值。若没有旧文件，按 README 生成新 `.env`，但恢复后需重新登录并重配工作区 Provider 密钥。
2. 启动一个空的 MySQL 容器：`docker compose up -d --wait mysql`。
3. 将数据库备份复制进容器，再导入到 `MYSQL_DATABASE`：

   ```powershell
   docker compose cp .\backups\database-YYYYMMDD-HHMMSS.sql mysql:/tmp/eoa-restore.sql
   docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql --user=root "$MYSQL_DATABASE" < /tmp/eoa-restore.sql'
   ```

4. 恢复素材文件到 API 使用的上传目录；API 容器启动后可执行：

   ```powershell
   docker compose cp .\backups\uploads-YYYYMMDD-HHMMSS api:/app/uploads
   ```

5. 启动/重建剩余服务并检查健康状态：

   ```powershell
   docker compose up -d --build --wait --wait-timeout 180
   docker compose ps -a
   .\scripts\smoke.ps1
   ```

恢复到已有数据的数据库前，先备份目标数据；不要盲目重复导入 SQL。备份必须来自同一套项目和兼容的迁移链。

### 密钥丢失的影响

- 保留原数据库和工作区 Provider 配置时，应恢复匹配的 `.env`，尤其是 `AUTH_SECRET_KEY`。
- 若数据库已恢复但 `AUTH_SECRET_KEY` 遗失，登录令牌会失效，工作区中加密存储的模型密钥也无法解密；重新登录并在“系统设置”里录入 Provider 密钥。
- 若数据库本身完全丢失且没有备份，原账号和业务数据无法从 Git 仓库找回。可重新部署、创建新管理员，再用“无线充经营演示”准备模拟数据。

## 离线镜像迁移

联网机器可在构建完项目镜像后运行 `scripts/export-images.ps1`；新机器放入生成的镜像归档后运行 `scripts/import-images.ps1`。导入镜像不包含 `.env`、数据库卷或素材内容，仍需单独初始化配置或恢复备份。完成镜像导入后可用 `docker compose up -d --no-build --pull never --wait --wait-timeout 180` 启动已归档的镜像。完全离线构建仍需另外准备依赖缓存。
